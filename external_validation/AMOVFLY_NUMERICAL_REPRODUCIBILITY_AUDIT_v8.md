# AMOVFLY numerical reproducibility audit v8

**Status:** **CLOSED — IMMUTABLE DESIGN OBJECT REQUIRED FOR DOWNSTREAM REPLAY**

## Question

Can the pre-outcome AMOVFLY design object be regenerated byte-for-byte on a later GitHub hosted runner using the same source code, Python version, NumPy/SciPy/Pandas versions, source frame, constants and seeds?

## Evidence

The successful confirmatory execution froze the design object at SHA-256:

`a5b241f9d17be696652f30968bb1b8a0d2138087674ac371866b606e8362696b`.

A later post-outcome sensitivity workflow first attempted to reconstruct this design under the same declared numerical package versions. The SHA guard failed before any sensitivity outcome was computed. The reconstructed object had SHA-256:

`fb060967389e08b7358a33c0478d6e19bfa7431ef5f8ed39b30f3ef03854c56d`.

A field-level comparison showed:

- identical standardization means and standard deviations;
- identical kernel bandwidth;
- identical source-code hashes and seed lineage;
- identical three certainty sentinels;
- different first-order inclusion probabilities for 254 of 257 units at tolerance `1e-12`;
- maximum absolute `pi_i` difference: **0.010841166253875684**;
- mean absolute `pi_i` difference: **0.0009194348870406242**;
- different example Local-Cube selected set under the same nominal seed.

The exact low-level numerical backend responsible for this drift was not isolated. The evidence is sufficient to show that package-version pinning alone does not uniquely identify the realized unequal-probability design on GitHub hosted runners.

## Fail-closed response

No tolerance was relaxed and the reconstructed `pi_i` values were not accepted. The post-outcome sensitivity was changed to download the immutable artifact from the successful confirmatory run, verify the original design-object SHA exactly, and use its frozen:

- `pi_by_unit_id`;
- certainty-sentinel indices;
- Split15 deterministic indices;
- Split15 audit inclusion probabilities and allocation;
- seed block and gate definitions.

The later sensitivity therefore changes only the diagnostic outcome definition. It does not regenerate or alter the confirmatory sampling design.

## Reproducibility rule

For KTES designs whose inclusion probabilities depend on floating-point novelty/ranking calculations, a reproducible execution package requires both:

1. pinned source/runtime metadata; and
2. the hashed realized design object containing the exact first-order inclusion probabilities and deterministic design identities.

Recomputing the realized design from package versions and seeds alone is not treated as equivalent evidence unless the resulting design-object hash matches exactly.

## Interpretation

This is an execution-reproducibility finding, not evidence against the statistical design itself. It strengthens the project provenance rule: downstream analyses must consume the frozen realized design object rather than silently replacing it with a numerically close reconstruction.
